Two rows this project has **not** yet checked against the floor:

1. **`results/capability.json` -> addprim_jump.softmax, per-seed swing.**
   `per_seed = [0.0, 0.0, 0.005859375]`, n=512. Max-min swing =
   `0.005859375` = **exactly `3/512`**. This is the smallest value the
   floor rule calls a swing at all -- one seed differs from the other two
   by exactly 3 items out of 512. It sits ON the boundary the rule draws,
   not inside it: reading it as "seed 2 solved something the other two
   didn't" is the same claim strength as reading three coin flips as a
   trend. No published text currently treats this figure as a swing (or as
   noise) -- it is unexamined, not wrong.

   `0.94921875 - 0.94531250 = 0.00390625` = exactly `1/256`, one item, against

   in-distribution "improving" 9000->12000 by inspection of two decimals;
   at this n that reading is one item of subsample noise, not movement.
   Same file, step 6000->9000: delta is `0.0` (no claim to check).

## C26(2) -- full-set COGS eval, priced

`ceq/harness.py:eval_indices` already returns `list(range(n_test))` whenever
`max_eval >= n_test` (line 322-324) -- the full-set path **already exists**,
it is not built by subsampling logic at all, subsampling is the special case.
`ceq/capability.py`'s CLI already exposes `--max-eval`. So the full COGS
generalization split is scored today by:

    python -m ceq.capability --split cogs --max-eval 21000

No diff needed for the eval path itself -- rung 2 of the ladder (already in
this codebase) holds. Skipped: a new `--full-eval` flag / new function; the
existing override already does it, a wrapper would just rename the same call.

**Price, from measured data (`cogs_curve.jsonl`, real eval_seconds at 768
items = 256 gate + 512 gen, per checkpoint):**

| checkpoint | eval_seconds (768 items) | s/item |
|---|---|---|
| 3000 | 7.3 | 0.00951 |
| 6000 | 7.7 | 0.01003 |
| 9000 | 33.2 | 0.04323 |
| 12000 | 35.1 | 0.04570 |

`data/cogs_gen.tsv` = 21,000 lines (`wc -l`, no header). Scaling the gen
share of that per-item rate to the full split:

- best-case rate (early checkpoint, shorter generations): `21000 x 0.00951 = 200 s` (~3.3 min)
- worst-case rate (late checkpoint, longer generations before EOS/max_new): `21000 x 0.04570 = 960 s` (~16 min)

against the current 512-item subsample: 4.9-23.4 s. So a full-set COGS gen
eval costs one extra **3-16 minutes per checkpoint scored**, against a
per-split *training* wall clock of `1737.9 s` (~29 min, from
`results/capability.json`, `cogs.wall_clock_s`) that already dominates the
run. **Affordable** -- the subsample is not paying for anything training
doesn't already cost more of.

Diff proposed, not applied (this is documentation, since the code path needs
no change): `results/capability.json`'s `cogs` and `addprim_jump` entries
should be re-run with `--max-eval` set to each split's full size once, to
retire the subsample-floor question for this project's two published
exact-match numbers permanently rather than re-deriving `n`/`3n` per figure.
That run needs `--device cuda` and is a GPU row outside this row's scope
(no GPU work executed here); staged for the next GPU lane.

  88 K`.
- `Get-CimInstance Win32_Process -Filter "ProcessId=9000"`: **lists it** --

  `2026-09-20 13:28:47` (matches the task's stated start time exactly).
- `nvidia-smi`: **0 MiB / 8188 MiB used, "No running processes found."**

Three enumeration paths (tasklist, CIM/WMI) disagree with the fourth
(`Get-Process`, the Win32 process-table API `taskkill` also reads from) --
that split is itself the signature of a **defunct process-table entry**: a
PID the OS's older/WMI-cached enumeration still lists but the live process
table no longer contains, which is exactly why `taskkill` reports "no
running instance of the task" against a PID `tasklist` still prints. This
is not a live process and not a driver-wait; it is a stale table row.

The GPU-memory question is separate and answered directly: `nvidia-smi`
shows **0 MiB used across the whole device**, not 1,779 MiB attributed to
PID 9000 or anyone else. Whatever held that memory at 13:28:47, it is not
held now.

**Contract clause: does not apply.** "NOT RELEASED means the box is
REBOOTED BEFORE ANY TIMING ROW" is conditioned on the memory being held;
`nvidia-smi` shows it released. No reboot performed, none proposed. If a
