# kaggle/

`ceq_v17k.ipynb` — the CEQ round v17-K Kaggle notebook. Reproduces the
certified local RTX 4060's readings on Kaggle's GPU; never decides a
research number itself.

Read `V17_NOTEBOOK.md` at the repo root before touching this notebook — it
has the cell-by-cell walkthrough, the dependency list (what this notebook
calls that isn't finished yet), and the launch checklist. Nobody who wrote
these files ran the `kaggle` CLI, pushed a kernel, or touched `~/.kaggle`;
launch is the author's own call, after Gate 0 is green.

## Attach list — item 3, CORRECTED

**Item 3 said enwik8 is a private upload of the canonical
`http://mattmahoney.net/dc/enwik8.zip`, with the Kaggle mirror struck. The
reasoning stands; the outcome does not — a licence-clean Kaggle dataset now
carries the same bytes, so there is nothing left to upload.**

- **The mirror-striking rule is unchanged and still binding.** `nightfury1103/enwik8`
  stays struck — unlicensed, zero votes. Two more candidates were checked on
  the same grounds and struck for the same reason: `lanceni/enwik8` is
  exactly 100,000,000 bytes but its licence reads unknown; `nguyenatu/enwik8`
  is `apache-2.0` but its dataset is BPE tokenizer JSONs, not the corpus;
  `yorkyong/text8-zip` is unknown-licence `text8`, a different (lowercased,
  punctuation-stripped) cut of the same prize corpus. All three are recorded
  in `results/k_data_manifest.json["rejected"]` alongside `nightfury1103`,
  each with its own reason, same as every other struck slug.
- **`jamesmcguigan/hutter-prize` clears the bar the mirrors failed.** Licence
  **CC-BY-SA-3.0**, one file, `enwik9`, 1,000,000,000 bytes. **enwik8 IS the
  first 100,000,000 bytes of enwik9**, by the Hutter Prize's own definition —
  not assumed here: the first 100,000,000 bytes of that dataset's `enwik9`
  were measured this box, this session, against a verified local copy and
  hash to `2b49720ec4d78c3c9fabaee6e4179a5e997302b3a70029f30f2d582218c024a8`,
  **byte-identical to the pin already in `results/k_data_manifest.json`**
  `[MEASURED]`. The pin does not move — it was already correct.
- **The 90/5/5 split reproduces exactly over the same bytes.** Re-running
  `ceq.kdata.split_by_article` over the real slice lands the same
  article-snapped offsets as before: train/val at **90,042,869**, val/test at
  **95,000,818** `[MEASURED]` — same bytes in, same offsets out, asserted
  rather than re-derived.
- **This removes the only private upload the round needed.** Every other
  source on the attach list was always a public Kaggle attach or a
  regenerated bed; enwik8's move to `jamesmcguigan/hutter-prize` means
  nothing in this round is uploaded by hand.

`ceq/kdata.py`'s `sources.enwik8` now reads `kind: kaggle_attach_sliced`,
`dataset: jamesmcguigan/hutter-prize`, `member: enwik9`, `slice_rule: "first

## Attach list — item 4, CORRECTED (RULING 7)

**Item 4 asked for BED-M "as the intact 211,765-line file (not regenerated;
hash-pinned)". There is nothing to attach, and nothing was created to make the
description true.**

- **No such file exists.** Every file in this working tree over 1 MB was
  line-counted; exactly one has **211,765** lines and it is
  `data/tinystories_20k.txt` — 18,167,706 bytes, TinyStories, **not a chain
  corpus** (`V17_G05_DATA.md` §6 `[MEASURED]`).
- **BED-M has no on-disk artifact at all.** It is `ceq/corpus.py::build()`, named
  as BED-M by `ceq/beds/__init__.py:3`. There is no line-oriented file for it to
  be "intact" as.
- **`211,765` is TinyStories' line count attached to the wrong corpus.** The two
  nearest items on the attach list — item 4 (the beds) and item 5 (TinyStories)
  — appear to have crossed. Uploading `data/tinystories_20k.txt` in item 4's
  place would be the wrong corpus *and* would duplicate item 5.

**The regime, per Ruling 7:** BED-M is carried as **generator + seed + expected
hash, regenerated and asserted in-notebook — exactly the regime BED-K and BED-1
are already in.** On Kaggle **the hash assertion IS the provenance.** All three
beds are regenerated by `ceq.kdata.bed_signature` in the notebook's hash-verify
cell; **none of the three is uploaded, and there is no `/kaggle/input/` mount
point for any of them.**

Pins cited from `results/k_data_manifest.json` (`sources.*`, all three
`kind: generator`, `status: PINNED`), not retyped from memory:

| bed | generator | kwargs | sha256 (`results/k_data_manifest.json`) |
|---|---|---|---|
| **BED-M** | `ceq.corpus.build` | `n_train=384, n_test=128, seed=0` | `2f282a5d0e9ac412b9644e19969590c0f855e5ccb3db73436364bcb925f7d24d` |
| **BED-K** | `ceq.beds.bed_k.build_delay` | `n=500, d=4, seed=7` | `15de94b47ba07e8b2d118deac26306689a7c55d0b243699e7d04e0881a5c56e4` |

Each digest is taken over the full manifest dict the generator returns,

running it twice** (`ceq/kdata.py`, `bed_signature` called twice and compared).

**What still needs attaching is unchanged and is not affected by this
correction:** the three Kaggle-side sources still requiring a dry-run pin
(`lichess_chess_games`, `lichess_chess_evaluations`, `tinystories_cdla`). Those
ship at `status: UNPINNED_AWAITING_KAGGLE`; the notebook's hash cell **prints**

pin is an error and never a silent skip. Only after those digests are copied
into `results/k_data_manifest.json` and committed is the hash being
**asserted** rather than measured. `enwik8` is no longer in this group — per
item 3 above, it is a Kaggle attach (`jamesmcguigan/hutter-prize`) already
pinned and asserted, the same as the beds, not something still awaiting a
first run.
